# Claude handoff — как передавать работу между чатом и Claude Code

## Зачем этот файл

Чат и кодовый агент не должны зависеть от памяти конкретной сессии. Все решения, необходимые для следующего этапа, фиксируются в GitHub.

## Базовый цикл

`обсуждение в чате → production brief → approval → Claude Code → render/QA → design review → approval → publish → metrics → learning`

## Что обязан оставить чат перед передачей в Claude Code

Для каждого production brief должны быть явно зафиксированы:

- `id`;
- `platform`;
- `format`;
- `status`;
- конкретный вопрос/эксперимент;
- зачем материал нужен читателю;
- что именно проверяем для контент-завода;
- фактура и источники, которые разрешено использовать;
- exact copy или явное указание, какие поля ещё не утверждены;
- количество слайдов/сцен и narrative structure;
- арт-концепция;
- visual references с `use_for`;
- разрешённые final assets;
- thumbnail requirement для feed;
- performance intent;
- definition of done;
- `publish: false` по умолчанию.

Если хотя бы один критичный пункт не определён, Claude Code не должен угадывать его самостоятельно.

## Минимальный front matter

```yaml
---
id: example-id
platform: instagram
format: carousel
status: brief-review
publish: false
experiment:
  question: "Конкретный вопрос эксперимента"
  factory_node: "какой узел проверяем"
  decision_rule: "по чему решим: оставляю / дорабатываю / не беру"
---
```

Рекомендуемые статусы:

- `idea`
- `brief-review`
- `approved-for-render`
- `rendered`
- `design-review`
- `approved-for-publish`
- `scheduled`
- `published`
- `measured`
- `learned`

## Что делает Claude Code после `approved-for-render`

1. Читает `CLAUDE.md` и все обязательные source-of-truth файлы.
2. Проверяет, что brief действительно имеет `approved-for-render`.
3. Не меняет exact copy.
4. Определяет, можно ли использовать существующий layout family или нужен новый.
5. Рендерит production asset.
6. Делает технический QA.
7. Делает visual QA: overflow, contrast, safe zones, readability.
8. Для feed делает thumbnail preview; для карусели — contact sheet.
9. Проверяет, что соседние/последние обложки не повторяют ту же композиционную механику, если данные доступны.
10. Возвращает пользователю результат на `design-review`.
11. Не публикует.

## Что нельзя переносить только через чат

Не считать надёжной передачей:
- «мы это обсуждали выше»;
- «используй тот вариант, который мне понравился»;
- «сделай как прошлый пост»;
- устное упоминание asset без сохранённого идентификатора/пути;
- незафиксированную правку copy.

Если решение влияет на production, оно должно оказаться в GitHub brief/config.

## После design review

Пользователь может:

- утвердить без изменений;
- попросить локальную визуальную правку;
- вернуть к арт-дирекшену;
- вернуть к тексту/смыслу.

Если меняется смысл или copy, единица снова проходит через `brief-review` и новый approval на render.

## Публикация

Публикационный агент/чат обязан перед действием показать:
- точные final assets;
- точный caption;
- площадку/формат;
- дату и время;
- что именно будет опубликовано.

Только после явного пользовательского подтверждения менять статус на `approved-for-publish` и ставить материал в очередь.

## Learning loop

После появления достаточных метрик сохранить в brief или отдельный analytics artifact:
- reach;
- watch/retention для Reels;
- saves/shares для каруселей;
- качественные наблюдения;
- что подтверждено/опровергнуто в эксперименте;
- решение для узла завода: `оставляю / дорабатываю / не беру`;
- следующий конкретный тест.

Следующая публикация должна иметь право использовать этот learning как фактуру, но не обязана механически повторять лучший performance-приём.
