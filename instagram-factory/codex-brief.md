# Brief for Codex — alexsmoley Content Factory

Ты работаешь над производственной системой личного Instagram `alexsmoley`. Текущая задача — проверить её на собственном блоге. Не добавляй обещание будущей услуги или продажи брендам без отдельного решения пользователя.

## Source of truth

Перед работой прочитай все файлы в `instagram-factory/`. Не восстанавливай правила фирстиля по памяти и не придумывай недостающие дизайн-решения молча.

Обязательные глобальные правила для любого нового feed/Reels production:

- `content-strategy.md` — задача блога и роль форматов;
- `human-topic-rules.md` — human-first выбор и формулировка тем;
- `writing-contract.md` — обязательный тон и редакторская проверка любого нового текста;
- `brand-system.md` — фирменная система;
- `design-direction.md` — визуальная грамматика;
- `visual-references/README.md` — правила работы с внешними визуальными референсами;
- `performance-principles.md` — hooks, retention, share/save logic и performance QA для каруселей/Reels;
- конкретный content brief — exact copy, art direction и ограничения единицы контента.

## Human-first content contract

До production нужно убедиться, что тема проходит `human-topic-rules.md`.

Правильная последовательность:

**человек → конкретный эпизод/наблюдение → история → вывод → метод**.

Нельзя превращать методологию в генератор безличных тем. `Контент-завод`, `цех`, `ОТК`, `pipeline`, `human-in-the-loop` — не обязательные слова в каждом материале.

Если тема звучит как учебная программа, B2B-презентация или универсальный AI-гайд, а в ней нет конкретного опыта/наблюдения автора, останови production и зафиксируй проблему вместо самостоятельного «улучшения» темы.

Performance применяется после human-first фильтра и не может заменить живой источник темы.

## Writing contract

До фиксации exact copy проверь текст по `writing-contract.md`.

- Начинай с факта, наблюдения, вывода или действия.
- Убирай пустые подводки, пафос, псевдоафоризмы и искусственно рубленый ритм.
- Не придумывай автору профессию, роль, продукт или план.
- Для клиентского опыта пиши `писал для`, если другая роль не подтверждена.
- Используй `контент-завод` только для обозначения всего производственного процесса.
- Сохраняй человеческий голос после сокращения.

Если copy ещё не утверждён и не проходит контракт, оставь материал на `brief-review`. Если copy уже утверждён, не меняй его сам: зафиксируй конфликт и запроси редакторское решение.

Если локальный brief конфликтует с performance-принципами по тексту или смыслу, **не переписывай approved copy сам**. Зафиксируй конфликт и дождись редакторского решения. Performance-принципы не дают права менять утверждённый текст.

## Visual reference contract

Внешние визуальные референсы — это слой арт-дирекшена, а не библиотека готовых картинок.

Перед визуальным production:

1. Прочитай `visual-references/README.md` и релевантные файлы из `visual-references/`.
2. Если в content brief есть `visual_references`, для каждого референса используй только явно описанное поле `use_for`.
3. Не копируй уникальную композицию, фотографию, иллюстрацию, логотип или авторскую графику один в один.
4. Pinterest, Cosmos и любые похожие сервисы считай источником референсов, но не автоматическим источником production assets.
5. Если `rights_status` равен `reference-only` или `unclear`, изображение нельзя использовать в финальной публикации как asset.
6. Если референс не объясняет, что именно в нём берём, не используй его как арт-дирекшен.
7. Внешний референс не может отменять `brand-system.md` и `design-direction.md`.

Правильный путь:

**идея → смысл → 3–5 референсов → разбор конкретных приёмов → собственная композиция → renderer → QA**.

Неправильный путь:

**нашли красивую картинку → сделали почти так же**.

Если production требует внешнюю фотографию/иллюстрацию как финальный asset, а права не подтверждены, остановись и запроси лицензированный/собственный источник вместо молчаливого использования картинки.

## Performance contract

### Для каруселей

Renderer/production должен позволять проверять не только пиксельную корректность, но и narrative structure:

- сильный cover / first slide;
- slide 2 сразу подтверждает обещание cover;
- каждый middle slide добавляет новую информацию;
- payoff/финал закрывает hook;
- есть save-worthy или send-worthy элемент, если это соответствует задаче;
- никакого forced CTA и algorithm bait.

### Для Reels

Production должен учитывать:

- содержательный first frame без заставки;
- hook ясен примерно за первые 3 секунды;
- сюжет понятен человеку без знания предыдущих публикаций;
- каждая сцена даёт смысловой прогресс;
- текст физически успевает считываться;
- payoff сильнее или конкретнее setup;
- motion помогает смыслу, а не маскирует его;
- loop допустим только если естественен;
- никаких recycled-platform aesthetics, водяных знаков, AI-китча или algorithm bait.

Если возможно, включать эти пункты в machine-readable QA metadata конкретной единицы контента.

## Работа с текстами постов

Тексты не передаются через случайный промпт. Для каждого материала есть отдельный Markdown production brief.

Codex не переписывает утверждённый caption и не добавляет текст на визуал, если соответствующее поле не указано в content brief.

## Жёсткие ограничения

- Никаких самовольных декоративных слов и подписей.
- Не менять font family на похожий.
- Не добавлять стрелки/навигацию без функции.
- Не менять лицо/внешность на фото.
- Не публиковать без явного approval на этапе MVP.
- Не хранить секреты/API keys в репозитории.
- Не коммитить файлы шрифтов без проверки лицензии.
- Не оптимизировать под алгоритм ценой качества бренда и смысла.
- Не подменять живой авторский опыт искусственно придуманной «экспертной» темой.
- Не использовать Pinterest/Cosmos/reference-only изображения как финальные assets без понятных прав.

## Definition of Done для новой единицы контента

- тема прошла human-first фильтр `human-topic-rules.md`;
- новый текст прошёл `writing-contract.md`;
- exact approved copy сохранён;
- визуал соответствует brand/design rules;
- если использованы внешние референсы, каждый имеет понятный `use_for`, а права на финальные assets проверены;
- performance structure проверена по `performance-principles.md`;
- технический QA зелёный;
- performance QA зелёный или явно зафиксированы исключения;
- готовый asset можно передать в очередь публикации;
- публикация не происходит без отдельного approval.
