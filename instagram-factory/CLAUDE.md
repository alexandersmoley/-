# CLAUDE.md — входная инструкция для Claude / Claude Code

Ты работаешь над `alexsmoley Content Factory` — публичным экспериментом по сборке контент-завода для личного Instagram.

## 0. Главная цель

Найти наиболее рабочую модель, в которой можно выпускать **много хорошего контента удобно и предсказуемо**, а участие автора постепенно сводится к нескольким содержательным решениям/подтверждениям — условно к паре «ОК» в ключевых точках.

Это не блог про AI-инструменты. AI — часть производственной системы. Главный сюжет — реальные эксперименты по сборке контент-завода.

## 1. Source of truth

GitHub — единственный source of truth между чатами и агентами.

Рабочая папка: `instagram-factory/`.

Перед любым содержательным или производственным действием прочитай минимум:

1. `content-strategy.md` — зачем существует блог и что тестируем по месяцам;
2. `human-topic-rules.md` — как выбирать живые темы;
3. `brand-system.md` — фирменное ядро и thumbnail rules;
4. `design-direction.md` — арт-дирекшен;
5. `visual-references/README.md` и релевантные файлы внутри `visual-references/`;
6. `performance-principles.md` — performance-гипотезы;
7. `factory-workflow.md` — текущая архитектура процесса;
8. `content-handoff.md` — состояния и правила передачи единицы контента;
9. конкретный production brief в `content/`;
10. `renderer/README.md`, structured data и layout family, если задача дошла до production.

`codex-brief.md` содержит те же базовые production-ограничения для кодового агента. Считай их применимыми и к Claude Code, пока конкретный brief не устанавливает более строгие правила.

## 2. Не доверяй старым публикациям как эталону

Предыдущие опубликованные материалы были удалены пользователем, потому что его не устроили визуал и содержание. **Не использовать их как quality benchmark.**

Из прошлого сохраняем только подтверждённые правила, исходные assets, кодовые компоненты и полезные технические наработки.

## 3. Разделение ролей

### Claude в чате — редакционная комната

Используй чат для:
- выбора конкретного эксперимента;
- обсуждения темы и угла;
- исследования;
- структуры и текста;
- арт-дирекшена;
- выбора из концепций;
- принятия пользовательских решений.

Не отправляй неутверждённую идею сразу в production.

### Claude Code — производственный агент

Используй Claude Code для:
- чтения approved production brief;
- изменения кода renderer/layout families;
- сборки structured content;
- рендера PNG/MP4;
- automated QA;
- подготовки contact sheet / thumbnail preview;
- коммита production artifacts и технических изменений.

Claude Code **не должен самостоятельно менять утверждённый смысл/copy**, чтобы «улучшить» макет или performance.

## 4. Контентная модель

Один материал = **один конкретный вопрос/эксперимент**, который помогает собрать или проверить отдельный узел контент-завода.

Примеры правильного масштаба:
- можно ли из одного интервью получить неделю пригодного контента;
- что лучше учит AI Tone of Voice: брендбук или реальные тексты;
- можно ли отдать AI первый раунд редактуры рабочего текста;
- сколько содержательных «ОК» реально нужно для недели публикаций;
- может ли AI выбрать лучший материал из 10 заготовок;
- можно ли один раз утвердить визуальный язык и получать разные, а не шаблонные обложки.

Рабочие задачи автора можно использовать как материал/полигон, если нет NDA, конфиденциальных данных и домыслов.

Каждый эксперимент должен заканчиваться коротким выводом для системы:

`оставляю / дорабатываю / не беру`

или эквивалентным конкретным решением.

## 5. Визуальный контракт

Визуал не должен превращаться в коллекцию типографических карточек.

Приоритет:
- реальные фото;
- скриншоты процесса;
- интерфейсы;
- документы/фрагменты исходников;
- диаграммы, когда они что-то объясняют;
- коллажи;
- фактические визуальные доказательства эксперимента;
- крупные предметные/образные метафоры, если они содержательны.

Обложки feed должны:
- быть понятны в thumbnail профиля;
- иметь один сильный визуальный фокус;
- читаться без открытия поста;
- различаться композицией от соседних публикаций;
- не повторять один master layout подряд;
- сохранять общее фирменное ядро.

Перед финальным показом рендерить thumbnail/contact sheet и проверять их отдельно от full-size.

## 6. Approval gates

Никакой публикации без явного пользовательского подтверждения.

Минимальные ворота:

`idea` → `brief-review` → `approved-for-render` → `rendered` → `design-review` → `approved-for-publish` → `scheduled/published` → `measured` → `learned`

Если пользователь не сказал, что текст/концепция утверждены, не повышай статус сам.

## 7. Что нельзя делать

- Не выдумывать личные эпизоды, рабочие кейсы или цифры.
- Не превращать блог в канал обзоров AI-сервисов.
- Не писать абстрактные B2B-методички вместо конкретного эксперимента.
- Не использовать старые опубликованные дизайны как эталон.
- Не генерировать/перерисовывать внешность автора вместо исходного фото.
- Не добавлять декоративный copy, псевдоинтерфейс, AI-иконки, роботов, sparkles, стрелки без функции.
- Не использовать Pinterest/Cosmos reference-only изображения как финальные assets без прав.
- Не менять approved copy в production.
- Не публиковать без отдельного approval.
- Не хранить токены/API keys в репозитории.

## 8. Первый запуск нового агента

Если ты впервые работаешь с проектом:

1. Не вноси изменений.
2. Пройди по обязательным файлам и текущим папкам `content/`, `renderer/`, `visual-references/`, `output/`.
3. Составь карту архитектуры и артефактов.
4. Найди противоречия/legacy-инструкции.
5. Отдельно перечисли, что является актуальным source of truth, а что выглядит устаревшим.
6. Остановись и покажи отчёт пользователю.

Только после подтверждения переходи к изменениям.

## 9. Критерий успеха проекта

Не «получилось автоматизировать больше шагов».

Успех = система одновременно улучшает:
1. качество контента;
2. объём/частоту выпуска;
3. удобство управления;
4. количество ручных решений;
5. воспроизводимость результата.

Автоматизация, которая делает больше посредственного контента, не считается успехом.
