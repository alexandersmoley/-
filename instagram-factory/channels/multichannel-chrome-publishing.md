# Multichannel production + Chrome publishing

## Назначение

Этот файл — обязательная инструкция для Claude / Claude Code, когда одна тема одновременно готовится для нескольких каналов и/или публикуется через браузер.

Текущие целевые каналы:

- Instagram `alexsmoley`;
- Telegram `@a_smoley`;
- vc.ru `https://vc.ru/id5738265`.

Главный принцип: **одна утверждённая фактура → три самостоятельных материала → отдельный QA каждого канала → единый human review → публикация только после явного ОК.**

Одновременная подготовка не означает копипаст. Одновременная публикация не означает три слепых клика подряд.

# 2. Что значит «одна тема на три площадки»

Нельзя брать один текст и механически растягивать/сокращать его.

Общими между каналами остаются:

- подтверждённые факты;
- личный опыт автора;
- основной тезис;
- исходные фото/скриншоты/документы;
- ограничения и запреты;
- дата/контекст события;
- утверждённые формулировки, если пользователь решил сохранить их везде.

Отдельно собираются:

### Instagram

Визуальный формат: Reel / carousel / feed post / Stories. Текст должен работать вместе с визуалом. Caption не обязан пересказывать весь материал.

### Telegram

Самостоятельный короткий/средний текст. Быстро к сути, разговорно, без лекции. Карточки/видео — дополнение, если они реально нужны.

### vc.ru

Самостоятельная длинная статья с контекстом, деталями, структурой и доказательствами. Читатель должен понять её без Instagram и Telegram.

# 3. Master brief

Каждая мультиканальная тема начинается с одного master brief.

Рекомендуемое место:

`content/topics/<slug>-master-brief.md`

В master brief фиксировать:

- `id`;
- что реально произошло;
- почему тема выходит сейчас;
- подтверждённые факты;
- что является мнением/наблюдением автора;
- ссылки на источники и assets;
- что нельзя утверждать;
- основной тезис;
- возможные углы для каналов;
- список уже approved формулировок;
- ограничения по визуалу;
- статус;
- publication intent.

Master brief не должен содержать выдуманную фактуру ради «полноты».

---

# 4. Channel packages

Из master brief создать отдельные channel packages.

Пример структуры:

```text
content/topics/<slug>-master-brief.md
content/telegram/<slug>.md
content/vc/<slug>.md
reels/<slug>.json              # если Instagram = Reel
carousels/<slug>.json          # если Instagram = carousel
posts/<slug>.json              # если Instagram = static/feed post
content/multichannel/<slug>.publication.json
```

Если существующая структура конкретного формата уже иная — не ломать её ради этого примера. Важен принцип: источник фактов один, channel copy раздельный.

---

# 5. Publication manifest

Для мультиканальной темы рекомендуется единый manifest:

```json
{
  "id": "topic-slug",
  "status": "draft",
  "sourceBrief": "../topics/topic-slug-master-brief.md",
  "channels": {
    "instagram": {
      "enabled": true,
      "format": "reel",
      "status": "rendered",
      "publish": false,
      "copySource": "...",
      "assets": ["..."],
      "publishedUrl": null
    },
    "telegram": {
      "enabled": true,
      "status": "approved-copy",
      "publish": false,
      "copySource": "../telegram/topic-slug.md",
      "assets": ["..."],
      "publishedUrl": null
    },
    "vc_ru": {
      "enabled": true,
      "status": "approved-copy",
      "publish": false,
      "copySource": "../vc/topic-slug.md",
      "assets": ["..."],
      "publishedUrl": null
    }
  }
}
```

`publish:false` у любого канала — абсолютный запрет на финальный клик для этого канала.

Не использовать один общий `publish:true`, если пользователь утвердил публикацию не везде.

# 6. Workflow подготовки

Базовый маршрут:

`master brief → 3 channel drafts → channel QA → visuals → technical QA → unified preview → human approval → Chrome preflight → publish approval → sequential publish → verification → URLs → analytics`

## Этап A. Разобрать тему

1. прочитать master brief;
2. проверить фактуру;
3. определить, что в истории общее для всех каналов;
4. выбрать отдельный угол/структуру для каждого канала;
5. не начинать production, если реальной фактуры недостаточно.

## Этап B. Подготовить три версии

Можно делать параллельно, но каждая версия проходит собственный writing QA.

Запрещено:

- копировать Instagram-caption в Telegram как финальный текст;
- публиковать Telegram-пост как vc.ru-статью после добавления H2;
- писать три разных фактических версии одной истории;
- менять цифры/результаты между каналами;
- усиливать факт в одном канале ради кликабельности.

## Этап C. Визуалы

Использовать один asset pool, но выбирать визуалы по задаче канала.

Instagram может требовать motion/card production.
Telegram может использовать часть тех же карточек/видео.
vc.ru может использовать обложку, схемы, скриншоты и иллюстрации внутри статьи.

Не создавать три комплекта декоративных AI-картинок, если одна содержательная схема/скриншот решает задачу лучше.

## Этап D. Unified preview

Перед публикацией пользователь должен получить один review bundle:

- Instagram: preview/contact sheet/video + caption;
- Telegram: финальный текст + media preview в правильном порядке;
- vc.ru: статья + обложка + иллюстрации + browser draft/preview;
- список того, что будет опубликовано в каждом канале;
- явное указание, где `publish:false`.

Claude не должен заставлять пользователя собирать финал по пяти разным сообщениям/файлам, если это можно показать единым пакетом.

# 7. Approval model

Обязательные ворота:

1. тема/master brief;
2. exact copy каждого канала;
3. визуал;
4. публикация.

Один пользовательский ОК может закрыть несколько ворот только если из формулировки это однозначно следует.

Примеры:

- `текст ок` → только copy approval;
- `визуал ок` → только design approval;
- `готово, публикуй в телеграм` → Telegram publish approval;
- `всё ок, публикуй все три` → publish approval для Instagram + Telegram + vc.ru, если пользователь видел финальные версии всех трёх;
- `закинь на гитхаб` → не publish approval;
- `подготовь к публикации` → не publish approval.

Если пользователь изменил текст после approval, соответствующий канал возвращается минимум в `approved-copy` / visual recheck и требует новый preflight.

# 8. Chrome как публикационный adapter

Для этого workflow Chrome — поверхность реального аккаунта. Claude работает через уже авторизованную пользовательскую сессию.

Целевые сайты:

- `https://www.instagram.com/`;
- `https://web.telegram.org/`;
- `https://vc.ru/`.

## 8.1. Сессии и учётные данные

Никогда:

- не просить пользователя положить пароль в файл;
- не коммитить cookies/tokens/session storage;
- не копировать Chrome user profile в репозиторий;
- не хранить 2FA codes;
- не обходить CAPTCHA;
- не пытаться восстанавливать/угадывать пароль;
- не отправлять session data в логи.

Если требуется вход — пользователь логинится вручную в Chrome. После этого Claude продолжает.

## 8.2. Работа с существующим Chrome

Предпочтительный маршрут:

1. использовать уже открытый авторизованный Chrome;
2. подключаться к нужным вкладкам через доступный browser/Chrome control;
3. перед любым вводом проверить домен, аккаунт и страницу;
4. не открывать новый чистый профиль без необходимости;
5. не использовать headless для финального publish, пока production-контракт явно не разрешил это и поведение не доказано серией успешных запусков.

Если прямого управления пользовательским Chrome нет — остановиться и вернуть конкретную недостающую возможность. Не подменять это незаметно новым Playwright-профилем с отдельной авторизацией.

## 8.3. Селекторы

Не строить production-автоматизацию только на случайных classname.

Приоритет:

1. role / accessible name;
2. label / placeholder;
3. стабильный текст интерфейса;
4. URL/path;
5. DOM-семантика;
6. classname — только как последний вариант.

Если UI изменился — сначала inspect/screenshot/map, потом правка adapter. Не кликать наугад.

# 9. Preflight в Chrome

До финального publish подготовить три вкладки/черновика настолько далеко, насколько можно без выхода материала в паблик.

### Instagram preflight

- открыт правильный аккаунт `alexsmoley`;
- выбран правильный тип публикации;
- загружены точные final assets;
- порядок media верный;
- caption совпадает с approved source;
- cover выбран правильно, если формат его требует;
- виден экран непосредственно перед публикацией;
- сделан screenshot.

### Telegram preflight

- открыт канал `@a_smoley`;
- текст вставлен полностью;
- media загружены и стоят в правильном порядке;
- ссылки/абзацы/форматирование проверены;
- виден экран перед `Send`;
- сделан screenshot.

### vc.ru preflight

- открыт аккаунт `id5738265`;
- создан/открыт правильный draft;
- title/subtitle/body перенесены полностью;
- cover/illustrations установлены;
- тема/раздел выбраны осознанно;
- текст browser draft сверён с source;
- виден экран перед финальной публикацией;
- сделан screenshot.

Если хотя бы один канал не дошёл до валидного preflight, не выдавать «всё готово к публикации».

# 10. Реальная публикация: последовательная, а не слепо параллельная

После общего `publish all three` не нажимать три кнопки одновременно.

Причина: после каждого клика нужно убедиться, что публикация действительно вышла и не получить дубликаты при retry.

Маршрут:

1. зафиксировать commit SHA/source versions всех трёх материалов;
2. проверить `publish:true` у трёх каналов;
3. сделать последний preflight screenshot;
4. публиковать **по одному каналу**;
5. после каждого канала получить подтверждение/URL;
6. записать результат в manifest/report;
7. только затем переходить к следующему.

Точный порядок можно менять под задачу. По умолчанию выбирай порядок, который минимизирует риск потери подготовленного состояния в браузере. Не заявляй «опубликовано везде», пока не проверены все три результата.

---

# 11. Проверка после публикации

Для каждого канала обязательно:

### Instagram

- публикация появилась в правильном профиле;
- нужный Reel/carousel/post открывается;
- media/cover/порядок корректны;
- caption не потерял содержательный текст;
- сохранить URL.

### Telegram

- сообщение появилось в правильном канале;
- media и текст видны;
- ссылки работают визуально/по href, если это доступно проверке;
- сохранить permalink.

### vc.ru

- статья опубликована от правильного аккаунта;
- title/body/images присутствуют;
- выбран нужный раздел;
- сохранить URL.

Если UI после клика непонятен, не считать публикацию успешной только потому, что кнопка была нажата.

---

# 12. Идемпотентность и защита от дублей

Перед retry любого publish:

1. проверить manifest: есть ли `publishedUrl`;
2. проверить страницу профиля/канала;
3. искать совпадение по заголовку/первой фразе/времени;
4. если материал уже существует — не публиковать повторно;
5. записать найденный URL и продолжить verification.

После сетевой ошибки всегда сначала проверять фактический результат. Нельзя автоматически повторять финальный клик.

---

# 13. Частичный сбой

Пример: Telegram опубликован, Instagram опубликован, vc.ru упал до клика.

Claude должен вернуть точное состояние:

```text
Instagram: published — <url>
Telegram: published — <url>
vc.ru: failed before publish — draft saved
```

После частичного сбоя:

- не удалять уже опубликованные материалы без отдельного запроса;
- не дублировать успешные каналы;
- сохранить draft/preflight проблемного канала;
- исправить только сломанный adapter/этап;
- запросить новый publish approval только если финальный материал изменился или возникла неоднозначность.

# 14. Channel-specific browser notes

## Instagram

Chrome используется только для финальной сборки/публикации уже готовых assets. Не редактировать approved copy внутри Instagram «на глаз».

Если browser UI не поддерживает нужный production-формат или теряет качество/функции, остановиться и предложить существующий publishing service route. Не ухудшать формат молча.

## Telegram

См. `telegram.md`.

Особенно проверять правильный канал: Telegram Web легко оставить на последнем открытом чате.

## vc.ru

См. `vc-ru.md` и `vc-ru-draft-automation.md`.

vc browser adapter обязан уметь сначала собрать draft и сравнить его с source. Финальный publish разрешается только по правилам раздела approval + при `publish:true`.

# 15. Что записывать в GitHub после браузерного прогона

Не записывать credentials/session data.

Можно и нужно записывать:

- channel statuses;
- source commit SHA;
- asset paths + hashes при необходимости;
- время preflight;
- время публикации;
- published URLs;
- расхождения браузерного редактора с source;
- screenshots только если они не содержат чувствительные данные;
- ошибки adapter;
- manual steps, которые пришлось сделать пользователю;
- learning для следующего запуска.

Рекомендуемый report:

`output/multichannel/<slug>/publication-report.json`

Пример:

```json
{
  "id": "topic-slug",
  "sourceCommit": "...",
  "channels": {
    "instagram": {"status": "published", "url": "..."},
    "telegram": {"status": "published", "url": "..."},
    "vc_ru": {"status": "published", "url": "..."}
  },
  "manualActions": [],
  "warnings": []
}
```

# 16. Команда пользователя «сделай публикации для трёх площадок»

Интерпретировать как production request, а не как мгновенное разрешение публиковать.

Claude должен:

1. взять следующую утверждённую тему / конкретный master brief;
2. собрать три самостоятельных версии;
3. сделать QA;
4. собрать визуалы;
5. подготовить browser drafts/preflight;
6. показать единый финал;
7. получить явное publish approval;
8. только затем опубликовать разрешённые каналы;
9. вернуть три URL и publication report.

Если пользователь сразу говорит: `возьми утверждённый финал и опубликуй его во всех трёх каналах`, новый editorial approval не нужен, если exact final уже однозначно определён и не менялся. Но browser preflight и проверки аккаунта обязательны.

# 17. Критерий успеха

Успешный multichannel run — это не «автоматизация дошла до конца».

Успех:

- одна фактура;
- три нормальных самостоятельных материала;
- точный source of truth;
- минимум ручной рутины;
- ни одной самовольной смысловой правки после approval;
- правильные аккаунты;
- отсутствие дублей;
- проверенные published URLs;
- понятный отчёт о том, где ещё нужен человек.

Целевая метрика проекта остаётся практической: **сколько содержательных ОК пользователя нужно, чтобы выпустить хороший материал на нескольких площадках.**
