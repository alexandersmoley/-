# vc.ru: Chrome draft + controlled publish

## Цель

После утверждения текста и визуалов Claude / Claude Code должен уметь через авторизованную сессию Chrome:

1. создать и заполнить черновик статьи в аккаунте автора;
2. вернуть preview и расхождения;
3. остановиться до отдельного publish approval;
4. после явного ОК и только при `publish:true` выполнить финальную публикацию;
5. проверить опубликованную статью и вернуть URL.

Аккаунт автора: `https://vc.ru/id5738265`.

Эта версия заменяет прежний абсолютный запрет на browser publish. **Default всё равно draft-only:** пока `publish:false`, финальный клик запрещён.

Для мультиканального запуска обязательно также читать `multichannel-chrome-publishing.md`.

## Источник

Для каждого материала:

- статья: `content/vc/<slug>.md`;
- publication manifest материала;
- master brief темы;
- правила площадки: `channels/vc-ru.md`;
- фирстиль: `brand-system.md` и `design-direction.md`;
- `writing-contract.md`.

## Что должна сделать автоматизация до публикации

1. Проверить статус текста: `approved-copy` или выше.
2. Прочитать `publish` для `vc_ru`.
3. Проверить наличие готовой обложки и иллюстраций из manifest.
4. Открыть авторизованную сессию vc.ru в Chrome.
5. Проверить, что активен аккаунт автора `id5738265`.
6. Создать новую статью или открыть существующий draft этого материала.
7. Заполнить заголовок и лид/подзаголовок из manifest/source.
8. Перенести статью в редактор vc.ru с сохранением структуры:
   - H2/H3 → заголовки редактора;
   - обычный Markdown → абзацы;
   - `-` → маркированные списки;
   - цитаты → цитатный блок только если это реальная цитата/сноска;
   - строки со схемами → отдельный блок, не ломая текст.
9. Загрузить обложку.
10. Расставить иллюстрации в местах, заданных manifest/brief.
11. Выбрать утверждённую тему/раздел. Если нужная тема недоступна — остановиться и вернуть варианты, не выбирать наугад.
12. Сверить browser draft с исходником.
13. Сделать screenshot/preflight.
14. Вернуть ссылку на черновик, если vc.ru её даёт, и отчёт.
15. При `publish:false` остановиться здесь.

## Сверка browser draft

Проверить с исходником:

- заголовок;
- подзаголовок/лид;
- все H2/H3;
- все абзацы;
- все пункты списков;
- ссылки;
- порядок иллюстраций;
- CTA;
- тему/раздел;
- отсутствие случайных повторов/дублированных блоков.

Если потерян хотя бы один содержательный блок, draft считать неготовым.

Автоматизация не должна «дописать по смыслу» то, что не перенеслось. Нужно исправить перенос и снова сравнить.

## Publish gate

Финальная публикация разрешена только если одновременно выполнено всё:

1. пользователь видел финальный текст и visual package;
2. material status = `approved-for-publish`;
3. в manifest для `vc_ru` стоит `publish: true`;
4. browser draft прошёл сверку;
5. выбран правильный аккаунт;
6. выбран правильный раздел/тема;
7. preflight screenshot сделан непосредственно перед финальным кликом.

`publish:false` — абсолютный запрет.

Фразы `сделай статью`, `подготовь`, `создай черновик`, `закинь в vc`, `подготовь к публикации` сами по себе не дают право нажимать финальную публикацию.

Фразы `публикуй эту статью`, `выкладывай на vc`, `публикуй все три` могут считаться publish approval, если exact final однозначно определён и пользователь уже видел его.

## Финальный browser publish

После approval:

1. ещё раз проверить URL/domain и аккаунт;
2. ещё раз сравнить title + первую/последнюю часть статьи + количество основных блоков;
3. проверить cover и illustrations;
4. проверить тему/раздел;
5. нажать финальную кнопку публикации один раз;
6. дождаться результата;
7. открыть опубликованную статью;
8. проверить title/body/images;
9. сохранить published URL;
10. записать status = `published` в publication report/manifest, если этот файл предназначен для технического статуса.

После сетевой ошибки **не повторять клик автоматически**. Сначала проверить профиль/страницу и убедиться, не вышла ли статья уже.

## Защита от дублей

Перед retry:

- проверить `publishedUrl` в manifest/report;
- проверить профиль автора;
- найти материал по заголовку/первой фразе;
- если статья уже опубликована — записать URL и не публиковать повторно.

## Безопасность Chrome-сессии

- пароль vc.ru не хранить в репозитории;
- cookies/session storage не коммитить;
- Chrome profile не копировать в проект;
- 2FA/CAPTCHA проходит пользователь вручную;
- не обходить защиту платформы;
- session/token данные не писать в логи.

Если авторизация слетела — остановиться, попросить пользователя войти в Chrome и продолжить после этого.

## Статусы

`approved-copy → visuals-ready → vc-draft-created → vc-draft-reviewed → approved-for-publish → published → measured → learned`

Переход `vc-draft-reviewed → approved-for-publish` делает только человек.

## Что показала проба API (30.08.2026)

Проба `scripts/vc-api-probe.mjs`, запущенная из GitHub Actions, была read-only — ни одной записи не создано.

Проверенные факты:

- `https://api.vc.ru/v2.31` и `https://api.vc.ru/v2.1` отвечают JSON;
- `/v1.9` — 404;
- `/subsite/subscriptions` — 200 без токена;
- `/subsite/me` — 401;
- `/uploader/upload` — 405 на GET, то есть endpoint существует и ждёт POST;
- проверенные варианты `/entry/create`, `/entry/new`, `/entry/draft`, `/entry/drafts`, `/entry`, `/entries`, `/writing/create`, `/writing` — 404 на обоих префиксах.

Вывод: публичный API в проверенной форме не дал endpoint создания записи. Рабочий production route — браузерная автоматизация в сессии автора.

Если понадобится снова исследовать API, не угадывать endpoints. Сначала посмотреть DevTools → Network во время реального сохранения draft и зафиксировать фактический запрос.

## Скрипты из репозитория

Исторически подготовлены команды:

```text
pnpm vc:draft:login
pnpm vc:draft
pnpm vc:draft:inspect
```

Их роль — вспомогательный browser adapter / диагностика, а не источник прав на публикацию.

Если прямое управление пользовательским Chrome доступно, предпочитать текущую авторизованную Chrome-сессию по правилам `multichannel-chrome-publishing.md`.

Не создавать новый скрытый профиль с отдельной авторизацией, если задача требует работы именно через Chrome пользователя.

## Селекторы и UI

Не завязываться только на случайные classname.

Приоритет:

1. role/accessible name;
2. label/placeholder;
3. стабильный текст интерфейса;
4. URL/path;
5. DOM-семантика;
6. classname как последний вариант.

Если редактор изменился — сначала inspect/map/screenshot, потом чинить adapter. Не кликать наугад.

## Что вернуть пользователю

### После draft/preflight

- ссылку на draft, если доступна;
- screenshot;
- список расхождений;
- что пришлось упростить;
- готовность/неготовность к publish;
- `publish:false/true`.

### После публикации

- published URL;
- screenshot опубликованной статьи;
- точный status;
- предупреждения/расхождения;
- что было сделано вручную, если пользователь вмешивался.

## Текущий принцип

vc.ru остаётся длинным самостоятельным каналом. Browser automation снимает ручную верстку и публикационный хвост, но не получает права менять approved copy или публиковать без человеческого ОК.
