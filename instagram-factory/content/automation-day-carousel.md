# Пост: «Я потратил почти день, чтобы автоматизировать один пост»

Этот файл — **единственный production brief для поста**. Он должен содержать достаточно контекста, чтобы Codex/renderer могли собрать карусель без копирования текста из чата и без додумывания требований.

## Задача поста

Показать первый реальный прогон контент-завода через конкретные сбои и вывести главный принцип:

> **Автоматизировать нужно не создание каждого поста, а производственную систему вокруг него.**

Это не жалоба на инструменты и не «провал дня». Это инженерный разбор того, как из набора ИИ-инструментов начала появляться производственная система.

## Фактическая основа

Использовать только эти реальные события:

1. Дизайн оказался нестабильной частью процесса: генерация идеи макета не равна стабильной production-вёрстке.
2. Закончился лимит Codex, после чего стало очевидно, что Codex не должен быть обязательным звеном для каждого поста.
3. GitHub Pages сначала отдавал 404, а Metricool для публикации требовал публичный URL медиа.
4. После текстовых правок QA остановил рендер, потому что source of truth и structured renderer data разошлись.
5. После исправлений архитектура стала: идея → арт-дирекшен → GitHub → renderer → QA → публичный PNG → Metricool → Instagram.
6. Codex остаётся инженером системы: нужен для создания/изменения renderer и layout-family, но не для ежедневного выпуска каждого поста.

Не добавлять новые «факты», цифры, названия сервисов или причины сбоев, которых нет выше.

# Caption — exact approved copy

Вчера я почти целый день потратил на то, чтобы автоматизировать один пост.

Сначала это звучит как провал. Особенно если сам же и строишь контент-завод, который должен ускорять работу.

Но на практике именно такие дни и показывают, где у тебя система, а где просто набор инструментов.

На словах всё выглядело красиво: идея, текст, дизайн, публикация, аналитика. Хотелось собрать цепочку, в которой ИИ помогает на каждом этапе, а человек не делает всё руками, а управляет процессом.

На деле быстро выяснилось, что слабое место не в том, может ли нейросеть что-то написать или нарисовать. Слабое место — в стыках между этапами. Дизайн оказался нестабильным, Codex неожиданно стал критически важной частью процесса, GitHub Pages сначала не отдавал готовый файл, а потом система вообще остановила рендер из-за того, что я изменил текст.

И это, кстати, был хороший сбой. Потому что старый вариант не ушёл в публикацию случайно.

В итоге я понял простую вещь: автоматизировать нужно не создание каждого отдельного поста, а производственную систему вокруг него.

То есть не «пусть ИИ сделает мне контент», а «пусть система помогает превращать идею в хороший опубликованный материал и не даёт выпускать брак».

Сейчас мой контент-завод выглядит примерно так: идея → арт-дирекшен → контент в GitHub → renderer → автоматический QA → публичный файл → Metricool → Instagram.

И вот это уже гораздо больше похоже на рабочую конструкцию.

Так что день ушёл не на один пост, а на то, чтобы этот пост вообще смог появиться внутри нормального процесса.

# Art direction

## Core concept

**«Система ломается → система становится системой».**

Карусель должна ощущаться как editorial/process case study. Не как набор одинаковых карточек и не как презентация SaaS-продукта.

Визуальный нарратив:

1. обещание автоматизации;
2. простая схема;
3. первый разрыв — дизайн;
4. архитектурная зависимость от Codex;
5. разрыв между готовым макетом и публикацией;
6. QA впервые работает как производственный gate;
7. новая архитектура;
8. сформулированный принцип;
9. спокойный финал.

## Brand grammar

Использовать визуальную систему alexsmoley:

- editorial / web-magazine, не generic social templates;
- много воздуха;
- крупная типографика как основной визуальный инструмент;
- electric/royal blue + cream/light + black;
- Inter Regular — body/service;
- Cormorant Garamond Regular — display/editorial;
- Cormorant Garamond Italic — только осмысленный expressive blue accent;
- сетка/hairlines — только когда они структурируют систему или pipeline;
- без случайных декоративных линий;
- без pseudo-logo;
- без AI-иконок, роботов, мозгов, sparkles и другой нейро-символики;
- без теней, градиентов и декоративных карточек по умолчанию;
- без эмодзи;
- без CTA на слайдах;
- не добавлять служебные подписи вроде «ошибка», «шаг 1», «case study», если их нет в exact copy.

## Composition strategy

Не создавать 9 новых layout-family. Нужна **одна параметризованная family `process-diagram-carousel`** с несколькими композиционными режимами:

- `statement` — крупный тезис + supporting copy;
- `pipeline` — схема процесса;
- `breakpoint` — визуальный разрыв/стык процесса;
- `criteria-list` — production criteria;
- `closing` — чистая editorial типографика.

Слайды должны быть разнообразными по композиции, но явно одной серией.

- Slide 01: `statement`
- Slide 02: `pipeline`

- Slide 07: `pipeline` — главный системный слайд

## Visual mechanics

Разрешённые механики:

- типографический контраст;
- spatial sequencing;
- функциональные стрелки только в pipeline;
- controlled blue blocks, если они несут структурную функцию;
- hairlines только как process connections / divisions;
- намеренные разрывы линии/схемы на slides 04–06.

Запрещено:

- декоративные стрелки вне схем;
- логотипы GitHub, Metricool, Codex, Instagram;
- mock browser windows без смысловой необходимости;
- стандартные warning/error icons;
- красный как случайный «цвет ошибки»;
- случайные слова и подписи;
- визуальные метафоры «завода» с шестерёнками/конвейером;
- фотографии в этой карусели.

# Renderer implementation contract

Если `process-diagram-carousel` ещё не существует, Codex должен **один раз** добавить её как reusable layout-family. После этого будущие process/carousel-посты должны собираться без Codex, только из structured content.

## Required stack

- TypeScript/JavaScript + HTML/CSS/SVG;
- Playwright/Chromium deterministic screenshot;
- Sharp допустим для финальной PNG-оптимизации;
- production canvas строго 1080×1440 для каждого слайда;
- никаких image-generation моделей для production render;
- только реальные Inter Regular и Cormorant Garamond Regular/Italic из существующей factory setup.

## Structured source

После реализации renderer создать structured post source в принятом репозиторием формате (JSON/schema). Он должен:

- ссылаться на этот markdown как canonical content source;
- хранить checksum этого markdown;
- содержать exact slide copy из этого файла;
- содержать 9 slides;
- содержать layout family `process-diagram-carousel` и mode каждого слайда;
- иметь статус `approved-for-render` только после готовности renderer;
- не менять caption;
- `publish` всегда остаётся false до отдельного пользовательского approval.

## Output

Ожидаемые артефакты:

- `output/automation-day-carousel/slide-01.png` … `slide-09.png`;
- individual QA JSON для каждого слайда;
- series/carousel QA summary;
- contact sheet для быстрой человеческой проверки;
- публичные HTTPS URLs через существующий GitHub Pages output pipeline.

# Automated QA gates

Pipeline должен падать, если не выполнен хотя бы один gate:

1. Ровно 9 слайдов.
2. Каждый PNG ровно 1080×1440.
3. Exact copy: текст каждого слайда совпадает со structured source.
4. Structured source checksum совпадает с этим markdown.
5. Caption не изменён renderer/Codex.
6. Используются только разрешённые fonts.
7. Используются только разрешённые brand colors.
8. Нет overflow/crop текста за canvas/safe area.
9. Нет логотипов, эмодзи, случайных иконок, теней, градиентов, декоративных стрелок.
10. Functional arrows допускаются только на pipeline slides.
11. Нет фотографий.
12. Все тексты читаются на мобильном размере.
13. `publish` = false.
14. Contact sheet создан.
15. Все individual slide QA прошли.

Дополнительно для slide 07:

- вся последовательность pipeline присутствует полностью и в правильном порядке;
- стрелки/связи не создают неоднозначности;
- последний supporting paragraph не конфликтует со схемой по иерархии.

# Human acceptance criteria

Перед публикацией пользователь должен увидеть contact sheet или все 9 render PNG и отдельно подтвердить публикацию.

Проверить глазами:

- карусель ощущается как один editorial case study;
- не выглядит как девять копий одного шаблона;
- нет визуального «нейрослопа»;
- главный смысл считывается даже при быстром листании;
- slides 04–06 визуально показывают сбои/стыки без дешёвых error-метафор;
- slide 07 — кульминация системы;
- slide 09 — спокойный финал, а не CTA.
