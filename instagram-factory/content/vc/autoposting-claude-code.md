# Как я собрал себе контент-завод на ChatGPT и Codex

Последний закреп я прошёл почти целиком через ChatGPT, GitHub, Codex и Metricool. В ChatGPT собрал тему, структуру и текст. Утверждённую версию положили в GitHub. Codex собрал макеты и проверил их. После моего ОК пост ушёл на публикацию.

Код руками я для этого не писал.

Сейчас весь процесс выглядит примерно так:

`ChatGPT → Todoist → ChatGPT → GitHub → Codex → проверка → мой ОК → Metricool → Instagram`

Слово «контент-завод» пока звучит чуть солиднее самой конструкции. Но отдельные участки уже работают, и мне стало интересно довести это до нормальной системы.

> *Instagram принадлежит компании Meta, деятельность которой признана экстремистской и запрещена на территории РФ. С 1 сентября 2025 года размещение рекламы на ресурсах с ограниченным доступом в России запрещено. Здесь речь идёт о моём редакционном контенте, а не о рекламе.*

## Зачем мне вообще понадобился контент-завод

Я давно хотел регулярно вести блог, но каждый материал быстро превращался в маленький проект. Даже когда текст уже готов, дальше начинается хвост:

- найти нужную фотографию;
- проверить последнюю версию текста;
- собрать карточки;
- посмотреть превью;
- исправить косяки;
- экспортировать;
- подготовить подпись;
- загрузить всё в сервис публикации;
- ещё раз проверить;
- опубликовать.

Каждая операция небольшая. Вместе они отлично съедают время и внимание.

При этом просто генерация текстов через ИИ меня не очень интересует. Получить очередной пост по команде «напиши про пользу контент-маркетинга» можно было давно.

Мне хотелось проверить другое: можно ли выстроить процесс целиком — от темы до публикации и потом до аналитики.

То есть чтобы система помогала:

- придумывать темы;
- собирать контент-план;
- выбирать одну тему в работу;
- собирать фактуру;
- писать и редактировать текст;
- помнить мой тон;
- учитывать фирстиль;
- готовить макеты;
- проверять результат;
- публиковать;
- возвращать данные в следующий цикл.

Главный вопрос для меня сейчас простой: сколько содержательной работы можно отдать системе, не получив на выходе поток проходного контента.

## Что я называю контент-заводом

Для меня это не одна нейросеть и не один сервис. Это набор правил и инструментов, через которые материал проходит по понятному маршруту.

Сейчас роли распределены так:

- **ChatGPT** — контент-план, работа с темой, фактура, структура, текст и редактура;
- **Todoist** — очередь тем;
- **GitHub** — утверждённый контекст проекта и актуальные правила;
- **Codex** — техническое производство;
- **Google Drive** — исходники;
- **Metricool** — публикация.

Конкретные сервисы со временем наверняка поменяются. Меня больше интересует сама схема.

## Шаг 1. Сначала собираю контент-план в ChatGPT

Начинаю в чате. Здесь обсуждаю, о чём вообще стоит писать, какие темы можно объединить, какой формат подходит конкретной идее и что ставить в очередь первым.

В итоге появляется контент-план. После этого он уходит в Todoist.

Мне удобно разделять эти две функции: в ChatGPT я думаю и редактирую, в Todoist вижу очередь. Когда пора делать новый материал, беру оттуда одну тему и возвращаюсь с ней в чат.

## Шаг 2. Одну тему довожу до нормального текста

Вот здесь пока много моего участия. Я приношу фактуру: что реально сделал, что произошло, что хочу показать, какие детали важны, где сам пока не уверен.

Дальше вместе с ChatGPT разбираем:

- главный тезис;
- структуру;
- факты;
- формулировки;
- заголовок;
- формат;
- визуальную идею.

Текст проходит несколько кругов редактуры.

Если просто попросить ИИ «напиши пост про автоматизацию контента», довольно быстро появляются эффективность, масштабирование, новая эра и освобождение творческого потенциала. Обычно я это удаляю.

Поэтому работа с текстом у меня устроена вполне по-старому: черновик, правки, ещё правки, финальная версия. ИИ просто сильно ускоряет промежуточные операции.

## Шаг 3. Утверждённый материал складываю в GitHub

Когда тема, факты и текст меня устраивают, появляется бриф. Это обычный файл в GitHub.

В нём можно зафиксировать:

- тему;
- задачу материала;
- подтверждённые факты;
- утверждённый текст;
- правила тона;
- требования к визуалу;
- нужные исходники;
- ограничения;
- статус материала.

Для меня GitHub оказался одним из самых полезных элементов всей схемы. Чат отлично подходит для обсуждения. Хранить в нём окончательные решения неудобно.

## Почему вообще GitHub

Сначала идея складывать Instagram-посты в GitHub кажется слегка избыточной. Потом у тебя появляется двадцатое правило.

Например:

- эту конструкцию больше не использовать;
- этот шрифт только для крупных заголовков;
- фото не перерисовывать;
- синий использовать только функционально;
- утверждённый текст Codex не переписывает;
- публикация только после моего ОК.

Если всё это разбросано по чатам, через пару недель начинается археология.

Поэтому GitHub у меня стал местом, где хранится актуальная версия проекта. Там уже лежат отдельные документы с правилами по тексту, фирстилю, дизайну и производственному процессу.

Меняем правило один раз — следующий материал уже получает новую версию. Мне это нравится гораздо больше, чем идея одного волшебного промпта.

## Что надо загрузить в систему заранее

ИИ не угадает сам, как ты пишешь, что считаешь хорошим дизайном и какие решения тебя раздражают. Чтобы система начала работать хотя бы примерно в твою сторону, ей нужен контекст.

У меня постепенно накопился такой набор:

- описание блога;
- цели;
- аудитория;
- правила тона;
- список запрещённых и нежелательных конструкций;
- фирстиль;
- шрифты;
- цвета;
- референсы;
- фотографии;
- удачные тексты;
- неудачные примеры;
- правила производства;
- точки согласования.

Чем лучше собран этот слой, тем короче потом становятся команды.

## Шаг 4. ChatGPT и Codex связывает GitHub

У меня здесь есть довольно понятная граница. В ChatGPT я занимаюсь содержанием. Codex занимается производством. Между ними — GitHub.

Схема выглядит так:

`ChatGPT → GitHub ← Codex`

Мы с ChatGPT собираем и фиксируем утверждённый материал. Codex читает его оттуда.

Ему уже не нужно решать, что я хотел сказать. Это решено раньше. И желательно, чтобы он вообще не пытался в последний момент «улучшить» утверждённый текст.

## Шаг 5. Codex собирает готовые материалы

После брифа начинается техническая часть. Для карусели сейчас это примерно так:

`бриф → структура → рендер → проверки → превью`

Codex:

- читает бриф;
- читает правила проекта;
- получает нужные исходники;
- формирует структуру;
- собирает макеты;
- рендерит изображения;
- запускает проверки;
- готовит превью.

Я получаю не описание того, как могла бы выглядеть карусель, а реальные файлы. Для меня это и есть главное отличие от обычной работы с чат-ботом.

## Шаг 6. Проверки встроены в производство

Автоматизация без проверок довольно быстро превращается в способ быстрее производить ошибки.

Например, готовый макет не должен самовольно менять утверждённый текст. Если я утвердил «Я строю контент-завод», а в готовом макете внезапно появилось «Я создаю инновационный контент-завод нового поколения», это не творческая находка. Это ошибка.

Сборка должна остановиться.

Со временем хочу автоматически проверять хотя бы:

- совпадает ли текст с утверждённым;
- правильные ли размеры;
- не вылезает ли что-то за безопасную область;
- все ли файлы на месте;
- используются ли нужные шрифты;
- не сломались ли изображения;
- прошёл ли рендер без ошибок.

Вкус автоматическим тестом пока проверяется плохо. Размер картинки — вполне.

## Шаг 7. Потом всё равно смотрю я

После сборки материал не публикуется сразу. Сначала я смотрю превью.

Проверяю:

- нормально ли читается текст;
- устраивает ли композиция;
- правильно ли используется фотография;
- нет ли странных переносов;
- похож ли результат вообще на мой блог.

Если всё нормально — даю ОК. Если нет — возвращаемся на нужный этап.

Я пока специально держу человека внутри процесса. Мне интереснее сначала добиться стабильного результата, а потом сокращать количество проверок.

## Какие решения я пока оставил себе

Сейчас их четыре:

- **Тема.** Стоит ли вообще это делать.
- **Текст.** Так ли я хочу это сказать.
- **Дизайн.** Можно ли уже показывать людям.
- **Публикация.** Точно ли материал готов выйти.

Со временем какие-то из этих ОК могут исчезнуть. Но я хочу убирать их только тогда, когда конкретный этап много раз подряд работает нормально.

Полностью автоматическую фабрику посредственных постов можно собрать довольно быстро. У меня пока другая задача.

## Шаг 8. После ОК материал уходит в Metricool

После подтверждения готовый материал передаётся в Metricool. Дальше он публикуется в Instagram.

То есть мне уже не нужно вручную:

- скачивать карточки;
- искать их среди файлов;
- загружать;
- заново вставлять текст;
- проверять порядок изображений;
- собирать публикацию руками.

Именно этот хвост рутины мне хотелось убрать одним из первых.

## И это уже работает на реальном посте

Мой последний закреп прошёл через эту систему. Был контент-план. Из него выбрали тему. В чате собрали содержание. Утверждённые решения попали в GitHub. Codex собрал материал. Я посмотрел результат и дал ОК. После этого пост вышел.

По дороге многое пришлось чинить. Собственно, поэтому эксперимент пока и интересен.

## Что оказалось сложнее всего

Самое сложное — не публикация и даже не подключение сервисов. Сложно объяснить системе, что считать хорошим результатом.

Как я пишу. Какие слова не люблю. Насколько разговорным должен быть текст. Как должен выглядеть визуал. Какое фото подходит. Что можно менять. Что уже утверждено. Где надо остановиться и спросить меня.

На это сейчас и уходит большая часть работы.

После каждого неудачного результата появляется ещё одно правило. GitHub становится толще. Команды — короче. Вроде логично.

## Что я бы сделал иначе, если бы начинал сейчас

Сначала зафиксировал бы четыре вещи:

- тон;
- фирстиль;
- производственный процесс;
- точки согласования.

Потом выбрал бы один формат. Например, только карусели. Добился бы серии нормальных результатов. И уже после этого подключал видео, автоматическую публикацию, аналитику и новые площадки.

Я пошёл немного хаотичнее: что-то собрал, посмотрел результат, разозлился, написал ещё одно правило. Тоже метод.

## Где здесь вообще начинается «завод»

Для меня завод начинается в тот момент, когда очередной материал перестаёт быть новым проектом.

Есть тема. Система уже знает:

- где лежат правила;
- где взять факты;
- где искать изображения;
- как собрать формат;
- какие проверки пройти;
- где нужен человек;
- куда отправить результат.

Тогда команда действительно может стать короткой. Например: **«Возьми утверждённый бриф, собери карусель и подготовь её к публикации».**

Вся сложность находится не в этой команде. Она находится в системе вокруг неё.

## Следующий этап — несколько каналов из одной темы

Instagram для меня сейчас просто первый полигон. Следующая задача — научить систему работать с одной фактурой сразу для нескольких площадок.

Этот материал сначала появился как тема для Reels. Теперь из той же фактуры получилась статья для vc.ru.

Дальше можно сделать:

- Telegram-пост;
- материал для собственного блога;
- короткую публикацию;
- письмо;
- ещё один формат для соцсетей.

Если каждый раз всё начинается с пустого чата, завода пока нет.

Следующая версия схемы должна выглядеть примерно так:

`одна тема → главный бриф → Instagram / vc.ru / Telegram / блог`

Каждый канал получает отдельную адаптацию. Без копипаста: одна утверждённая фактура — несколько самостоятельных материалов.

Собственно, эта статья уже первый такой тест.

## Что хочу получить в итоге

Моя цель — постепенно дойти до системы, где можно написать: **«Возьми следующую тему из плана и подготовь её для Instagram, vc.ru и Telegram».**

Потом посмотреть результаты, несколько раз сказать «ок» и получить три готовых материала. А дальше подключить аналитику и посмотреть, что действительно сработало.

Если этот цикл станет стабильным, контент-завод можно будет переносить с моего блога на другие проекты: личные медиа, бренды и редакции.

Пока проверяю всё на себе. Так дешевле ошибаться.
